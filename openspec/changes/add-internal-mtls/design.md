# Design

## Context

Мотивация и объём — в `proposal.md`, требования — в `specs/`. Что есть сейчас
(проверено по коду и `compose.yaml`):

- Девять сервисов в одной сети `wallet-<env>`, все вызовы по `http://`. HTTP-серверы
  на `httplib::Server`, `SSLServer` нигде не используется.
- Клиентский TLS (`CPPHTTPLIB_OPENSSL_SUPPORT`) собран только у google-auth,
  wallet-ai, wallet-gateway, wallet-telegram. У wallet-api, wallet-report,
  wallet-mcp, wallet-docs его нет, хотя `libssl3` в образах есть.
- Общий код (`jwks.cpp`, `reports_client.cpp`) лежит в `wallet-common` и вендорится
  в каждый сервис скриптом `scripts/vendor.sh`.
- Клиенты `httplib::Client` создаются на каждый вызов, `set_keep_alive` нигде не
  вызывается, а по умолчанию `keep_alive_ = false` (клиент закрывает соединение
  после каждого запроса). Сервер держит keep-alive 5 с и до 100 запросов.
- healthcheck: `curl -f http://127.0.0.1:<порт>/healthz`; Prometheus (отдельный
  стек в сетях обоих контуров) ходит по `http://<сервис>-<env>:<порт>/metrics`.
- Секреты контура — в `~/.config/wallet-secrets/<env>/`, сгенерированное — в
  `WALLET_GENERATED_DIR` (пишет `infra/env/tls.sh`). Запуск — только через
  `infra/env/up.sh` / `deploy.sh`.
- Лимиты памяти 32–128 МБ на сервис, хост один (14 ГБ), GPU режимом не
  затрагивается.
- Критичный путь «токен по токену» (google-auth `token_exchange.cpp`, `telegram.cpp`,
  `mcp_tokens.cpp`): `/internal/telegram/token` выдаёт токен любого связанного
  пользователя, `/internal/token/exchange` выдаёт JWT на другой сервис, оба защищены
  общим `X-Service-Secret`, а **actor определяется именно секретом**
  (`identify_actor`). Секрет и Bearer идут по plain HTTP. Метрики и журнал обмена
  уже есть (`token_exchange_total`, `mcp_token_exchange_total`, `event=token_exchange`).
- Redis хранит активные access- и refresh-токены (30 дней) и запущен без пароля.
  Это отдельная от mTLS слабость, закрывается другим change до этого.

## Goals / Non-Goals

**Goals:**
- Шифрование и взаимная аутентификация сервис ↔ сервис внутри контура, включаемые
  настройкой контура; выключенный режим не меняет ничего.
- Идентичность вызывающего сервиса, достаточная для проверки прав на `/internal/*`.
- Минимум нового в рантайме: без sidecar-контейнеров, без внешнего CA-сервиса.

**Non-Goals:**
- k8s и service mesh (отдельное решение, когда стек уйдёт из compose).
- Пароль и ACL на Redis (отдельный change, делается до этого) и client assertion
  JWT вместо `X-Service-Secret` (отдельный change после, `TODO_service_auth_tls.md`,
  п. 1). Сегментация сети для `/internal/*` входит сюда (D11), для остального
  контура — нет.
- Защита от скомпрометированного хоста или контейнера с доступом к собственному
  ключу: mTLS защищает сеть между сервисами, а не сам сервис.
- Вызовы за пределы контура (LM Studio, Telegram API) и TLS на входе (`add-tls-ingress`).

## Decisions

### D1. Нативный TLS в httplib через общий слой в `wallet-common`

Один модуль `net/tls` в `wallet-common` создаёт сервер и клиент по переменным
`TLS_CERT`, `TLS_KEY`, `TLS_CA`: все заданы — `SSLServer` с обязательной проверкой
клиента / `SSLClient` с клиентским сертификатом и проверкой имени сервера; не
заданы — прежний `Server` / `Client`. Все 8 сервисов подключают модуль через
`vendor.sh`.

Альтернативы:
- *Sidecar-прокси (Caddy/stunnel) на каждый сервис* — без правок кода, но +9
  контейнеров по ~20–40 МБ при лимитах 64 МБ, сложнее healthcheck и сети.
- *Service mesh (Linkerd)* — прозрачно, но только k8s, в compose не работает.
- *Только TLS на входе* — не закрывает внутренний трафик и `/internal/*`.

Нативный вариант дороже по коду, но не умножает контейнеры и даёт идентичность
клиента в приложении, а она нужна для D4.

### D2. Мини-CA на `openssl`, скрипт в `infra/env/`

Скрипт `infra/env/mtls.sh` (рядом с `tls.sh`, вызывается из `up.sh`/`deploy.sh`):
- по CA на контур; закрытый ключ CA в `~/.config/wallet-secrets/<env>/mtls-ca/`
  (вне git, не монтируется в контейнеры), сертификат CA — в generated-каталог;
- на сервис ECDSA P-256, срок 30 дней, SAN: `<сервис>` и `<сервис>-<env>`,
  extendedKeyUsage `serverAuth, clientAuth`, CN = имя сервиса;
- отдельные сертификаты `prometheus` (клиент) и сертификат Postgres;
- повторяем: пока осталось больше половины срока, ничего не меняется.

Альтернативы: `step-ca` (лишний долгоживущий сервис ради 9 сертификатов) и общий
сертификат на все сервисы (ломает идентичность, D4). ECDSA, а не RSA — дешевле
рукопожатие, важно пока клиенты одноразовые (D6).

### D3. Файлы сертификатов — монтируются read-only

Каждому сервису монтируется только его пара (cert, key) и `ca.pem`. Сервис
читает их на старте; httplib не перечитывает файлы, обновление — через пересоздание
контейнера (compose пересоздаёт его сам, когда меняется метка вроде
`wallet.mtls-config` с хэшем сертификатов, как у `tls-proxy`).

### D4. Идентичность клиента → права на `/internal/*`

Сервер читает CN клиентского сертификата. google-auth держит таблицу «эндпоинт →
разрешённые сервисы» в конфигурации (в коде по умолчанию: `/internal/telegram/*` —
wallet-telegram; `/internal/mcp/token` — wallet-mcp, wallet-ai;
`/internal/token/exchange` — wallet-mcp, wallet-ai, wallet-telegram), нарушение —
403 и строка в журнале. Проверка идёт до проверки секрета и действует только в
режиме mTLS. Это именно авторизация: сертификат отвечает «какой сервис», а
пользовательский JWT или секрет — «за кого».

Там, где actor сегодня определяется секретом (`/internal/token/exchange`),
идентичность из сертификата обязана с ним совпасть: расхождение — отказ, оба
имени в журнал (без значения секрета). Так секрет перестаёт быть единственным
носителем идентичности, но остаётся вторым фактором до отдельного change
(client assertion JWT). Порядок включения — D12.

### D5. Healthcheck и метрики — по mTLS, без отдельного порта

Healthcheck: `curl --cacert … --cert … --key … https://<сервис>:<порт>/healthz`
(в образах curl уже есть; имя совпадает с SAN). Отдельный plain-порт не нужен, и
из сети эндпоинт закрыт (спека). У wallet-web (nginx) healthcheck — через
`curl`-совместимый вариант или отдельный `server`-блок на loopback, решается в
задачах. Prometheus получает клиентский сертификат каждого контура; его конфиг
генерируется скриптом (в режиме выключено — `http`, включено — `https` с
`tls_config` данного контура), метки `job`, `env` сохраняются.

Альтернатива — второй plain-порт на loopback внутри контейнера: правка кода
сервисов (второй `Server` в потоке) ради того, что решается конфигурацией.

### D6. Постоянные соединения на горячем пути

Гейтвей держит пул клиентов к каждому апстриму (`set_keep_alive(true)`, потоко-
безопасная выдача/возврат клиентов), с одной повторной попыткой на новом
соединении при обрыве (сервер закрывает простой через 5 с). SSE-потоки (чат) —
отдельный клиент на поток, мимо пула. Редкие вызовы (JWKS, `/internal/*`,
справочник счетов) остаются одноразовыми: handshake ECDSA стоит долей
миллисекунды, пул ради них не окупается. Решение подтверждается замером
loadtest до/после (спека: «Нагрузка не ухудшается заметно»).

### D7. TLS до Postgres и Redis — отдельный поздний этап

- Postgres: `ssl=on` с сертификатом контура, `pg_hba`: `hostssl` для всех,
  `hostnossl reject`, `clientcert=verify-ca` для ролей сервисов; миграторы,
  dumper, monitoring и администратор — по паролю роли, но только по TLS. Клиент
  libpq: `sslmode=verify-full`, `sslrootcert`, `sslcert`, `sslkey` в `DATABASE_URL`
  (правка конфигурации, не кода: `PQconnectdb` принимает URI).
- Redis: сначала пароль и ACL (отдельный change, **до** этого change), затем
  Redis 7: `tls-port` и `tls-auth-clients`. Как клиент Redis подключён в google-auth
  (библиотека, поддержка TLS), в этом change не проверено — выяснить в задачах;
  не поддерживает — исключение записать в README режима.

### D8. Защита от выката без поддержки

Образ, собранный с поддержкой TLS, получает метку `org.wallet.mtls=1`. `up.sh`
и `deploy.sh` при включённом режиме проверяют метку у каждого образа контура
(`docker image inspect`) и отказываются включать режим / выкатывать сервис без
неё, вместо падения healthcheck посреди выката.

### D9. Входной порт гейтвея — граница, а не внутренний сервис

Гейтвей — единственный сервис, у которого есть внешние клиенты: браузер и
телефон (напрямую или через `tls-proxy`), скрипты выката и smoke с хоста
(`127.0.0.1:<порт>`). Его входной порт остаётся как есть (за ним TLS ingress из
`add-tls-ingress`), а mTLS применяется к его клиентской стороне (вызовы к
апстримам) и к его `/metrics`. Для этого у гейтвея два слушателя: прежний
входной (plain, наружу) и служебный mTLS-порт для healthcheck и Prometheus.
Альтернатива «весь гейтвей на mTLS» ломает браузер, телефон и скрипты выката,
которым нечем предъявлять сертификат сервиса.

### D10. Модульность

Как у `tls` и `docs`: без `WALLET_INTERNAL_MTLS=true` нет сертификатов, монтирований
и изменений в compose (условные `env_file`/переменные, как `WALLET_GENERATED_DIR`
у TLS). Включение — на test, затем на prod, как у rc-релизов.

Исключение — служебный порт `/internal/*` google-auth (D11): он и сеть
`auth-internal` включаются отдельными настройками и раньше остального контура,
потому что на нём критичный путь. `WALLET_INTERNAL_MTLS=true` для остальных
сервисов включается позже и не требует его повторного включения.

### D11. `/internal/*` google-auth — отдельный порт и сеть `auth-internal`

Сегментация по сети без отдельного порта ничего не даёт: `/internal/*` и публичные
`/auth/*`, JWKS живут на одном `:8080`, а все сервисы контура видят google-auth по
имени. Поэтому google-auth получает **второй слушатель** (служебный порт) только
для `/internal/*`; он публикуется лишь в сети `auth-internal` (google-auth,
wallet-telegram, wallet-mcp, wallet-ai). Публичный порт остаётся для `/auth/*` и
JWKS, `/internal/*` на нём убирается последним шагом миграции. На переходе
служебный порт может принимать и plain, и TLS (см. D12): без этого нельзя
переносить клиентов по одному.
Альтернативы: единый порт без сегментации (любой контейнер сети достаёт
`/internal/*`) и отдельный сервис для `/internal` (лишний контейнер и
дублирование состояния google-auth — Redis, ключи).

### D12. Проверка идентичности — «наблюдение → отказ»

На служебном порту google-auth три состояния, переключаемые настройкой, без
пересборки:
1. **observe** — принимает plain и TLS, ничего не отклоняет, но на каждый запрос
   сверяет CN сертификата (если есть) с actor по секрету и пишет в журнал и
   метрику расхождения и запросы без сертификата;
2. **enforce-tls** — plain не принимается, расхождение CN и actor — отказ;
3. **enforce** — то же, и прав по таблице D4 (403).
Переходы выполняются на test, по критериям из D13; откат — обратная настройка,
токены пользователей не затрагиваются. Выбрано поэтапно, а не «сразу enforce»,
потому что одна опечатка в SAN или роли на критичном пути ломает бота или чат без
понятной причины.

### D13. Порядок по риску выдачи токенов

Что будет украдено при перехвате, то и защищается раньше. Порядок:

| # | Шаг | Риск, который закрывается |
|---|---|---|
| 0 | Проверить состояние prod: выкачены ли `/internal/token/exchange` и MCP-токены | не защищать то, чего нет |
| 1 | Пароль и ACL на Redis (**отдельный change**, зависимость) | Redis хранит refresh-токены без пароля |
| 2 | Служебный порт и сеть `auth-internal` (D11), пока без TLS | любой контейнер достаёт `/internal/*` |
| 3 | Слой TLS и выпуск сертификатов (режим выключен) | фундамент для остального |
| 4 | Пилот google-auth ↔ wallet-telegram: observe → enforce | токен **любого** пользователя по одному секрету |
| 5 | Цепочка обмена: wallet-ai → google-auth → wallet-mcp → google-auth, по звену | JWT на другой сервис, вложенный `act` |
| 6 | Закрыть `/internal/*` на публичном порту google-auth | остаточный путь в обход |
| 7 | Гейтвей → api, report, ai, mcp, web (пул клиентов) | Bearer и cookie пользователей по plain |
| 8 | JWKS-клиенты, Prometheus, healthcheck | публичные данные, низкий риск |
| 9 | Postgres и TLS до Redis | данные, но уже за паролями |
| 10 | Prod, тем же порядком | после полного прогона на test |

(Отказ от `X-Service-Secret` — отдельный change после этого, не шаг здесь.)

Критерий перехода между шагами 4–6: на test за заданный период (не менее суток
или пока пройдён сценарий привязки бота, обмена через чат, MCP-токена) нет
роста `invalid_client`, `invalid_grant`, `invalid_target` в
`token_exchange_total`, нет записей о расхождении CN и actor, чат и бот отвечают.
Откат каждого шага — настройка, без пересоздания данных.

## Risks / Trade-offs

- **Прописанные имена и алиасы.** Сертификат не покрыл имя, по которому
  обращаются (например, `host.docker.internal`) → отказ проверки. → Список SAN
  берётся из compose (имя + алиас), проверяется скриптом перед стартом.
- **Просроченный сертификат останавливает сервис.** → Обновление при каждом
  `up.sh`/`deploy.sh`, срок 30 дней, обновление при остатке менее половины;
  мониторинг срока (метрика или проверка в smoke) — отдельной задачей.
- **Handshake на каждый вызов при одноразовых клиентах.** → ECDSA, пул на
  горячем пути (D6), замер.
- **Лишняя память и CPU.** Сотни КБ на контекст SSL, десятки КБ на соединение;
  при лимитах 32–64 МБ запас невелик. → Замер до/после, `mem_limit` пересматривается.
- **Сборка C++ по одному сервису за раз** (параллельная сборка вешает хост),
  8 сервисов → длинный выкат. → Раскатывать по одному и по rc-тегам.
- **Деградация при смешанных версиях.** Контур в режиме mTLS не примет образ без
  поддержки. → Метка образа (D8) и порядок: сервисы сначала, режим потом.
- **Права файлов ключей.** Рабочая папка на NTFS (нет Unix-прав), контейнеры
  могут работать не от root. → Каталог сертификатов вне NTFS-папки репозитория
  (generated-каталог), права 0640 с владельцем под uid контейнера — проверить на
  первом сервисе.
- **Prometheus в двух контурах с разными CA.** Один конфиг, два набора
  сертификатов. → Генерация конфига скриптом, отдельная job-группа на контур;
  сохранение меток `job`/`env` проверить на test до prod.
- **Не заменяет авторизацию.** Любой сервис с действительным сертификатом
  вызывает свои эндпоинты. → D4 для `/internal/*`, остальное — как раньше JWT.
- **Переходный режим plain+TLS на служебном порту** оставляет окно, в котором
  обмен возможен без сертификата. → Окно короткое, только на test до шага 6,
  наблюдение (D12) показывает, кто ещё ходит plain; закрывается явно.
- **Ошибка в CN, SAN или таблице прав ломает выдачу токенов** (бот, чат). → Режим
  observe до enforce (D12), метрики и критерий перехода (D13), откат настройкой.
- **Состояние prod неизвестно** (по диаграмме обмен токена выкачен только на
  test). → Шаг 0 проверяет до начала работ, иначе порядок и список сервисов
  уточняются.
- **Redis без пароля остаётся открытым**, если его change не выполнен раньше. →
  Зависимость, без неё критичный путь не считается закрытым.

## Migration Plan

Порядок — по D13, шаги соответствуют группам в `tasks.md`.

1. Шаг 0 и Redis: проверить prod, выполнить change с паролем Redis.
2. Служебный порт google-auth и сеть `auth-internal` без TLS (D11); клиенты
   `/internal/*` переключаются на неё по одному.
3. Общий слой TLS в `wallet-common`, `infra/env/mtls.sh`, условная часть
   `compose.yaml`; режим выключен — поведение прежнее. Выкат сервисов rc-тегами,
   по одному.
4. Пилот и цепочка обмена на test: observe → enforce (D12), критерий перехода
   (D13); затем закрыть `/internal/*` на публичном порту.
5. Остальные сервисы и гейтвей, Prometheus и healthcheck, loadtest до/после.
6. Postgres и TLS до Redis — отдельным шагом на test.
7. Тот же путь на prod. Откат любого шага: выключить настройку и запустить
   `up.sh` — контейнеры пересоздаются на прежней схеме, данные не трогаются
   (спека: «Откат без потери данных»).

## Open Questions

- Срок сертификата 30 дней — достаточно ли редок `up.sh`/выкат, чтобы сертификаты
  обновлялись вовремя, или нужен отдельный таймер (cron в Jenkins).
- Нужен ли гейтвею служебный mTLS-порт (D9), если healthcheck и Prometheus
  допустимо выполнять на входном порту: решается при реализации, на спеку не влияет.
- Подключается ли k8s (`infra/k8s`) — в этом change не рассматривается; если
  понадобится, mTLS лучше решать mesh-слоем.
