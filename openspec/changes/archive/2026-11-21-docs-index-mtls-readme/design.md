# Design

## Context

`docs-index.sh` собирает JSON `{"files":[{path,content}]}` на хосте (`jq`) и отправляет его `docker exec -i wallet-docs sh -c 'curl … http://127.0.0.1:8089/docs/index/$1'`; токен берётся из окружения контейнера через файл заголовка (D2 исходного change). После включения mTLS (wallet-docs 0.1.5, `INTERNAL_MTLS=true` на test) сервис слушает 8089 только по TLS и требует клиентский сертификат, поэтому `curl` по `http://` получает «Empty reply» (код 52) и `-w` печатает `000`. Скрипт на любой сбой печатает последнюю строку ответа, то есть «000». Мотивация — в proposal.md.

Jenkins запускает скрипты через `jobs/lib/env_run.sh`: из checkout'а **выкатанного тега wallet-infra** контура (`<state>/<env>/infra`), а не из рабочей папки; пока такого checkout'а нет — из рабочей папки.

## Goals / Non-Goals

**Goals:**
- Заливка работает и с mTLS (test), и без него (prod) одним скриптом.
- README попадают в заливку, вид `ops` наполняется.
- Сообщение об отказе называет причину.

**Non-Goals:**
- Не менять wallet-docs (0.1.6 готов) и Jenkinsfile job'а.
- Не включать mTLS на prod и не открывать сервис без сертификата.
- Не заливать репозитории без `openspec/` (например `org`): их README в заливку не входят.

## Decisions

**D1. mTLS-запрос — изнутри контейнера с его собственным сертификатом.** Контейнер уже получает `TLS_CERT`, `TLS_KEY`, `TLS_CA` (режим включён) и сертификат с SAN `wallet-docs` и `wallet-docs-<env>`. Скрипт внутри `sh -c` проверяет `[ -n "${TLS_CERT:-}" ]`: есть — `curl --cacert "$TLS_CA" --cert "$TLS_CERT" --key "$TLS_KEY" https://wallet-docs:8089/…`, нет — прежний `http://127.0.0.1:8089`. Сеть и стек Jenkins в этом не участвуют: Jenkins только вызывает скрипт на хосте через сокет Docker, а `curl` запускает `docker exec` внутри контейнера `wallet-docs`, в его сети и с его окружением (поэтому `127.0.0.1` и имя `wallet-docs` разрешаются там, а не в Jenkins). Решение принимается внутри контейнера, поэтому скрипту не нужно знать, включён ли режим в `<env>.env` (одно место истины — окружение контейнера), и пути сертификатов не уходят в аргументы процессов хоста (`docker exec` получает тот же текст). Проверено вручную на test 2026-11-21: `PUT https://wallet-docs:8089/docs/index/wallet-infra` → `200`. Альтернативы: сертификат Prometheus или отдельный клиентский сертификат Jenkins — отвергнуты, это новый секрет и новая поверхность; хост-порт 8089 — на test не публикуется.

**D2. Имя `wallet-docs`, а не `127.0.0.1`.** Проверка имени по SAN: `127.0.0.1` в SAN нет. Внутри контейнера `wallet-docs` резолвится в собственный адрес по алиасу сети (проверено).

**D3. README — отдельный `find` по хосту.** К списку `openspec/**/*.md` добавляется `find "$dir" \( -name third_party -o -name node_modules -o -name .worktrees -o -name build -o -name vendor -o -name .git -o -name openspec \) -prune -o -type f -name README.md -print0`. `-type f` не следует за симлинками (как и для `openspec/`, D4 исходного change); `openspec` исключён, чтобы `README.md` внутри него не попал дважды (сервис всё равно не отнесёт его к `ops`). Сервер фильтрует те же каталоги сам, поэтому клиентский фильтр — оптимизация и защита лимита 16 МБ, а не граница безопасности.

**D4. Причины отказа через код `curl`.** `upload` возвращает код `curl` отдельно от HTTP-кода: `-w` печатает HTTP-код, `$?` `docker exec` — код `curl`. Сопоставление: `58/60/35/…` (ошибки TLS) → «TLS-рукопожатие не прошло», `52/56/7/28` → «сервис недоступен (curl N)», `0` и не-2xx → «wallet-docs ответил <код> <error>». Чтение файлов сертификата проверяется до запроса: `[ -r "$TLS_CERT" ]` в контейнере, иначе «сертификат контейнера не читается» без попытки соединения. Сообщение не содержит токена и значений путей сверх имён переменных.

**D5. Версия скрипта у Jenkins.** Скрипт берётся из выкатанного тега wallet-infra. Порядок: PR в wallet-infra → тег `vX.Y.Z-rc.N` → `deploy.sh test wallet-infra <тег>` обновляет checkout → job `docs-index` запускается вручную с `ENV=test`, `REPO=wallet-infra` и затем `all`. До выката тега job продолжит запускать старый скрипт — это ожидаемо, не ошибка.

## Risks / Trade-offs

- [README в индексе на prod до обновления wallet-docs] → сервис 0.1.4 посчитает README в `skipped`; сообщение в журнале не меняется, предупреждения нет (это не отказ).
- [Рост тела заливки] → README — десятки КБ на репозиторий; лимит 16 МБ проверяется скриптом как раньше.
- [Утечка внутренних деталей через README] → вид `ops` виден только `role: admin` (wallet-docs), в README секретов нет (скан 2026-11-21 по 54 файлам); новые README попадают в индекс автоматически, поэтому правило «секретов в README нет» остаётся за автором.
- [Сертификат контейнера истёк] → предупреждение «TLS-рукопожатие не прошло» и `UNSTABLE`; сертификаты перевыпускаются при выкате (спека `internal-service-tls`).
- [curl в образе wallet-docs] → уже используется исходной версией, новых зависимостей нет.

## Migration Plan

1. PR в wallet-infra с правкой скрипта, README и спеки; после слияния тег wallet-infra и выкат на test.
2. Ручной запуск job `docs-index` (`ENV=test`, `REPO=wallet-infra`), затем `all`; сборка `SUCCESS`, в журнале строки итога по каждому репозиторию.
3. Проверить вид `ops` в базе test и вопрос админским токеном (см. wallet-docs, change docs-ops-kind, задача 6.3).
4. Откат: вернуть прежний тег wallet-infra (`deploy.sh test wallet-infra <старый тег>`); данные индекса не затрагиваются.
