# db

Всё, что относится к самой базе (не к какому-то одному сервису) — конфиг
инстанса Postgres и скрипты вокруг него. Раньше `.env`/`.env.example` лежали
в корне репозитория рядом с `compose.yaml` — переехали сюда, чтобы всё
db-шное (креды, инициализация, миграции) жило в одном месте, а не было
размазано между корнем и этой папкой.

- **`.env.example`** — шаблон `db.env` контура
  (`~/.config/wallet-secrets/<prod|test>/db.env`, см. `../env/README.md`):
  пароли всех ролей Postgres (см. "Три роли" ниже). У prod и test значения
  разные. Секреты самих сервисов (`GOOGLE_CLIENT_ID` и т.п.) сюда не
  относятся — они в `<сервис>.env` того же каталога секретов.

- **`init-db.sh`** — прогоняется автоматически Postgres-образом при первой
  инициализации пустого volume (`/docker-entrypoint-initdb.d/`, см.
  `compose.yaml`): заводит обе app-роли, обе базы и права между ними (см.
  "Три роли" ниже). Саму схему (таблицы) больше не создаёт — это отдельный
  шаг, см. "Миграции" ниже.

- **`migrations/perf/`** — миграции базы истории нагрузочных прогонов.
  Миграции баз сервисов живут в их репозиториях и едут внутри их образов
  (`/migrations`); накатывает их `../env/migrate.sh`. См. "Миграции" ниже.

## Три роли

Не одна общая роль на всё и не две (роль на сервис + владелец = та же
bootstrap-роль образа postgres) — а именно три, с разными правами:

| Роль | Переменные в `.env` | Права | Кто использует |
|---|---|---|---|
| **Мигратор** | `MIGRATOR_POSTGRES_*` | Владеет обеими базами и схемой, единственная умеет DDL (`CREATE`/`ALTER`/`DROP`) | только `init-db.sh` (и будущие миграционные скрипты) — НИКОГДА никакой сервис |
| **google-auth** | `AUTH_POSTGRES_*` | Только DML на свои таблицы (`SELECT`/`INSERT`/`UPDATE`/`DELETE`) — ни DDL, ни `TRUNCATE` | сервис google-auth |
| **wallet-api** | `WALLET_POSTGRES_*` | То же самое, своя база | сервис wallet-api |

Почему не переиспользовать одну роль на разные базы (было раньше): роль
образа postgres, которую он заводит из `POSTGRES_USER`, — фактически
суперпользователь. Если бы сервис подключался ею же (пусть даже просто к
другой базе), скомпрометированный сервис получал бы доступ и к чужой базе
тоже — разделение баз без разделения учёток изоляцию только имитирует.
Поэтому у мигратора (единственной роли с DDL) и app-ролей (только DML)
разные учётки, и `MIGRATOR_POSTGRES_*` не появляется ни в одном `.env`
сервиса — только здесь.

Изоляция баз друг от друга — двумя слоями: собственно разные роли-владельцы
(app-роль одной базы физически не существует в контексте другой) и явный
`REVOKE CONNECT ... FROM PUBLIC` на каждой базе в `init-db.sh` (Postgres по
умолчанию даёт `PUBLIC` право `CONNECT` на любую новую базу — без явного
отзыва одна app-роль технически могла бы подключиться к чужой базе, пусть и
без прав что-то там прочитать). Мигратор эти отзывы не обходят только
потому, что он суперпользователь — это ограничение самого официального
образа postgres, не наша схема, тут не решается.

### Дополнительные роли (не входят в «три роли» выше)

Помимо мигратора и app-ролей — ещё три, все тоже bootstrap'ятся
`init-db.sh`, но по другому принципу (не "сервис владеет своей базой", а
"инструмент читает/пишет чужие данные с минимальными правами"):

| Роль | Переменные в `.env` | Права | Кто использует |
|---|---|---|---|
| **`postgres_exporter`** | `MONITORING_POSTGRES_*` | Только встроенная `pg_monitor` (SELECT на `pg_stat_activity`/`pg_stat_database`/... ) — ни строки доступа к данным пользовательских таблиц | сервис `postgres-exporter` (см. `../monitoring/prometheus.yml`, дашборд Grafana "Wallet Transactions — Overview") |
| **`perf_history`** | `PERF_POSTGRES_*` | DML на свои таблицы В СВОЕЙ, четвёртой базе (`perf_history` — история прогонов нагрузочного контура, не домен кошелька) | `wallet-report/loadtest/record_run.sh` |
| **`dumper`** | `DUMPER_POSTGRES_*` | Только встроенная `pg_read_all_data` (SELECT на все таблицы и последовательности) и `CONNECT` к базам auth, wallet, telegram, ai — ни одной записи, ни DDL | `../env/backup.sh` (дампы prod), `../env/test-refresh.sh` (дамп prod для перезаливки test) |

Читает `perf_history`-базу отдельная read-only роль `perf_reader` (под ней
ходит Grafana) — заводится не здесь, а самой миграцией `perf` (см.
"Миграции" ниже) — GRANT SELECT должен идти ПОСЛЕ CREATE TABLE, не до.

## Миграции

Схема (`roles`/`users` для google-auth, `wallets` для wallet-api,
`test_run`/`test_result` для истории нагрузочного контура) — версия­-
нированные `.sql`-миграции в `migrations/{auth,wallet,perf}/` (`perf` —
своя, отдельная от кошелька база `perf_history`, см. "Дополнительные роли"
выше и `../../wallet-report/loadtest/README.md`, "Performance DB"),
накатываются **отдельным шагом после** `init-db.sh` (не автоматически при
старте `db` — миграции, в отличие от bootstrap-а ролей/баз, должны быть
перезапускаемы на уже существующей базе при появлении новых файлов, а не
привязаны к первой инициализации пустого volume). Инструмент —
[golang-migrate](https://github.com/golang-migrate/migrate) (образ
`migrate/migrate`), не Flyway: не тянет JVM (в проекте его нигде больше нет)
и умеет откат (`down`) бесплатно — у Flyway Community это платная фича.

Сами сервисы схему не создают и не катят миграции — их роли лишены DDL (см.
"Три роли" выше); при старте они только проверяют, что таблицы уже есть
(`db::Database::verify_schema()` в каждом из них — см. их README,
"Персистентность"/"Своя БД"), и падают с понятной ошибкой, если нет, вместо
загадочного `permission denied` на первом реальном запросе. Значит, накат
миграций — обязательный шаг между «поднять `db`» и «поднять `google-auth`/
`wallet-api`» (раньше это делал сам `init-db.sh` неявно, при первом старте
`db`; теперь — явно, см. ниже).

Миграции баз сервисов (auth, wallet, telegram, ai) лежат в репозитории
сервиса (`<сервис>/migrations/`) и попадают в его образ (`COPY migrations
/migrations` в Containerfile). Накатывает их `../env/migrate.sh` — из образа
той версии, что выкатывается, поэтому схема всегда соответствует коду.
Обычно руками ничего запускать не нужно: миграции катят `../env/up.sh` (все
базы) и `../env/deploy.sh` (база выкатываемого сервиса, до обновления
контейнера; в prod — после дампа).

**Руками:**
```bash
bash infra/env/migrate.sh test wallet                # up из образа, что сейчас в tags.env
bash infra/env/migrate.sh test wallet - version      # "-" — тот же образ по умолчанию
bash infra/env/migrate.sh test auth - down 1         # откатить последнюю (только в test!)
bash infra/env/migrate.sh test perf                  # infra/db/migrations/perf
```

### Expand/contract: миграция совместима с предыдущей версией кода

Откат сервиса (`env-rollback`, или автоматический — при провале smoke)
возвращает **образ**, но **не схему**: `down`-миграции при выкате и откате
не выполняются. Значит, любая миграция должна работать и с новым, и с
предыдущим кодом сервиса:

- **Можно в одном релизе:** добавить таблицу, столбец (с `DEFAULT` или
  `NULL`), индекс; расширить тип; добавить значение в справочник.
- **Нельзя в одном релизе с кодом, который это использует:** удалить или
  переименовать столбец/таблицу, сделать столбец `NOT NULL` без значения по
  умолчанию, сузить тип. Это делается в два релиза:
  1. *expand* — новое рядом со старым, код пишет в оба и читает новое;
  2. *contract* — следующим релизом, когда в prod нет кода, читающего
     старое, — удалить старое.
- Перед каждой миграцией prod снимается дамп
  (`${WALLET_BACKUP_DIR}/prod/<база>/`), это последняя линия отката схемы.

`refresh_tokens` для google-auth в миграциях больше нет — переехали в Redis
(AOF-персистентность + volume, см. `compose.yaml` и `google-auth/README.md`,
"Персистентность"). На инстансах, поднятых до этого перехода, таблица могла
остаться в базе физически — ничего её сейчас не удаляет (понадобится
отдельная будущая миграция, если решите почистить), она просто больше никем
не используется.

**Следующая миграция** (например, `000002_*.up.sql`/`.down.sql`) — просто
новая пара файлов в `migrations/` репозитория сервиса со следующим номером;
выкат нового тега сервиса подхватит и накатит только то, что ещё не
применено (см. служебную таблицу `schema_migrations`, которую сам заводит
`golang-migrate` при первом запуске).

## Подключение к базе контура

Порты Postgres на хост не публикуются (спека deployment-environments,
«БД не торчит наружу»). Посмотреть данные — через `docker exec`:

```bash
docker exec -it wallet-test-db-1 sh -c 'psql -U "$POSTGRES_USER" -d wallet_api'
```

Для GUI-клиента (DBeaver и т.п.) — временный туннель только на localhost,
закрывается вместе с контейнером:

```bash
docker run --rm -it --network wallet-test -p 127.0.0.1:15432:5432 \
    alpine/socat tcp-listen:5432,fork,reuseaddr tcp-connect:db:5432
```

Логин и пароль — app-роль нужной базы из `db.env` контура; мигратор видит
и может менять всё, для «просто посмотреть» лучше app-роль.
